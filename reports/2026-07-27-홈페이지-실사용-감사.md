# 우강테크 홈페이지 실사용 준비도 감사

- 감사일: 2026-07-27 (Asia/Seoul)
- 코드 범위: `apps/web`, `apps/admin`, `packages/db` 및 이들과 직접 연결된 `supabase/migrations`, 루트 배포 설정
- 판정 기준: **동작함** = 현재 코드와 확인 가능한 설정만으로 목적 달성, **반쪽** = 경로는 있으나 설정·보존·오류처리·검증 중 핵심 일부가 빠짐, **안 됨** = 기본 비활성 또는 실운영에 필요한 핵심 경로가 없음
- 제한: 운영 Vercel 환경변수는 저장소에서 확인할 수 없다. 로컬 Supabase 키로 테이블 존재 여부만 조회하려 했으나 실행 환경의 네트워크 차단(`fetch failed`)으로 원격 DB 상태는 **미확인**이다. 고객 데이터 조회는 시도하지 않았다.

## 2. billing 라우트 3종

**판정: 안 됨**

PG는 **Toss Payments**다. SDK 주소와 API base는 각각 `apps/web/src/app/subscribe/[projectId]/SubscribeClient.tsx:81-84`, `apps/web/src/lib/toss.ts:1-16`에 있다.

세 라우트 모두 `NEXT_PUBLIC_FEAT_BILLING=on`이 아니면 즉시 404를 반환한다 (`apps/web/src/lib/features.ts:14-15`, webhook `:13-17`, cancel `:16-20`, cron `:15-19`). `.env.example`도 기본값을 `off`로 둔다 (`apps/web/.env.example:26`).

| 라우트 | 켰을 때 하는 일 | 판정 근거 |
|---|---|---|
| `api/billing/webhook` | Toss `PAYMENT_STATUS_CHANGED`를 받아 `billing_history`에 payment key 기준 upsert하고, 성공 시 구독 다음 결제일 갱신, 실패/만료 시 pause | `apps/web/src/app/api/billing/webhook/route.ts:38-92` |
| `api/billing/cancel` | Toss 결제 취소 API를 호출하지 않고 DB의 구독 상태를 `cancelled`, `next_billing_at=null`로 변경 | `apps/web/src/app/api/billing/cancel/route.ts:34-70`; 실제 Toss 취소 함수는 별도 존재하지만 미호출 `apps/web/src/lib/toss.ts:85-104` |
| `api/cron/billing` | 결제 예정 active 구독을 최대 100개 조회해 Toss billing API로 청구하고 이력/다음 결제일/실패 횟수를 갱신 | `apps/web/src/app/api/cron/billing/route.ts:30-139`, 실제 API 호출 `apps/web/src/lib/toss.ts:69-82` |

실운영을 막는 코드 사실:

- webhook 서명은 서명 헤더·전송시간·secret 세 값이 모두 있을 때만 검증한다. 하나라도 없으면 검증 없이 처리한다 (`apps/web/src/app/api/billing/webhook/route.ts:21-29`).
- cron은 `CRON_SECRET`이 있을 때만 인증한다. 없으면 누구나 GET으로 청구를 실행할 수 있다 (`apps/web/src/app/api/cron/billing/route.ts:21-28`).
- cancel은 사용자 세션/토큰을 검사하지 않는다. `customerId`도 선택값이라 생략하면 구독 ID만으로 취소 가능하다 (`apps/web/src/app/api/billing/cancel/route.ts:22-31`, `36-48`).
- 구독 시작 페이지도 인증이 없고 project UUID로 고객·결제 정보를 읽는다 (`apps/web/src/app/subscribe/[projectId]/page.tsx:9-23`, `45-52`).
- 첫 결제 금액은 success URL의 `monthlyKrw` query string을 받아 1만~100만원 범위만 확인한 뒤 그대로 결제한다 (`apps/web/src/app/subscribe/[projectId]/SubscribeClient.tsx:65-70`, `apps/web/src/app/subscribe/[projectId]/success/page.tsx:18-20`, `44-47`, `98-104`). DB 가격과 재대조하지 않는다.
- Toss 실 API 호출 코드이므로 단순 스텁은 아니다. 그러나 현재 기본 비활성이고 위 보안·금액 검증 문제 때문에 **실제 결제를 켜면 안 되는 상태**다.

- `supabase/setup_all.sql`은 `001`의 핵심 테이블과 `002` storage까지만 합친 구버전이다. `billing_history`, `toss_customer_key`, `customer_tier`, `family_code` 문자열이 전혀 없으므로 이 파일만 실행한 DB에는 `003`~`006`이 반영되지 않는다 (`supabase/setup_all.sql:66-500`; 해당 문자열 검색 0건).
- `packages/db/src/types.gen.ts`는 Supabase 생성 타입이 아니라 `export type Database = any` 임시 스텁이다 (`packages/db/src/types.gen.ts:1-12`). `quotes` 라우트도 새 컬럼 타입 미반영을 주석으로 인정하고 강제 캐스팅한다 (`apps/web/src/app/api/quotes/route.ts:217-223`).
- 서버 DB 클라이언트는 URL 또는 service key가 없으면 호출 시 throw한다 (`apps/web/src/lib/supabase.ts:12-19`, `35-41`). persistence/billing OFF면 lazy 구조라 일반 페이지 로드에는 영향이 없다.

## 4. `apps/admin`은 무엇이며 실제 접근 가능한가?

**판정: 안 됨**

`apps/admin`은 견적·프로젝트·고객·시공 파트너·결제 이력·디바이스·설정을 관리하는 별도 Next.js 앱이다. 메뉴 정의는 `apps/admin/src/components/Sidebar.tsx:4-14`, dashboard DB 조회는 `apps/admin/src/app/page.tsx:5-34`에 있다.

접근성과 보안:

- 로그인 페이지, auth/session 검사, middleware 파일이 저장소에 없다. `apps/admin/src/app/layout.tsx:13-21`은 인증 없이 모든 페이지를 렌더링한다.
- admin DB 클라이언트는 항상 `SUPABASE_SERVICE_KEY`를 사용해 RLS를 우회한다 (`apps/admin/src/lib/supabase.ts:4-10`).
- 변경 API도 인증 검사 없이 바로 service-role로 insert/update/delete한다: installer 생성 `apps/admin/src/app/api/installers/route.ts:7-23`, installer 수정/삭제 `apps/admin/src/app/api/installers/[id]/route.ts:7-47`, project 수정 `apps/admin/src/app/api/projects/[id]/route.ts:28-49`, quote 수정/계약 전환 `apps/admin/src/app/api/quotes/[id]/route.ts:10-94`.
- 루트 `vercel.json`은 `@lcd-pro/web`만 build한다 (`vercel.json:1-9`). CI도 web 타입체크/build만 한다 (`.github/workflows/deploy.yml:29-33`). admin 별도 배포 설정은 저장소에서 발견되지 않았다.
- 2026-07-27 외부 확인에서 `https://wooktech.co.kr`은 응답했지만 `https://admin.lcdpro.co.kr`의 실제 응답은 확인하지 못했다. 검색 결과도 없었다. 따라서 admin의 현재 인터넷 접근 가능 여부는 **미확인**이다.

결론: 배포 근거가 없어 현재 운영 도구로 접근 가능하다고 판정할 수 없고, 만약 그대로 공개 배포되어 있다면 인증 없는 service-role 변경 API이므로 즉시 차단 대상이다.

## 7. 빌드/타입체크

**판정: 동작함 (타입체크), 전체 build는 미실행**

1. 요청한 `pnpm -C apps/web exec tsc --noEmit`은 pnpm 9 실행기가 레지스트리 서명 확인을 위해 네트워크를 사용하려다 실패/timeout했다. 이는 TypeScript 코드 에러가 아니다.
2. 설치 없이 이미 존재하는 로컬 실행 파일로 아래를 실행했다.

```text
working directory: E:\전광판\pro\lcd_pro\apps\web
command: .\node_modules\.bin\tsc.CMD --noEmit --pretty false
exit code: 0
stdout/stderr: 없음
```

따라서 web TypeScript 검사는 통과한다. 다만 `packages/db/src/types.gen.ts:1-12`가 `Database = any`이므로 DB 테이블/컬럼 타입 오류는 이 검사로 검출되지 않는다. 사용자가 요청한 범위가 타입 오류 확인이므로 `next build`는 실행하지 않았다.

## 지금 당장 막힌 것(P0)

1. **리드 무손실 접수 보장이 없다.** `/api/lead`는 웹훅 실패·미설정에도 성공하고 저장 백업이 없다. `/api/quotes`도 기본 OFF에서 DB 미저장이고 webhook은 fire-and-forget이다. 운영 env에 유효한 webhook이 있다는 증거도 저장소에는 없다.
2. **운영 Supabase 마이그레이션 상태가 미확인이다.** 특히 `003`~`006`이 빠지면 billing과 새 견적 컬럼이 실패한다. `setup_all.sql`만 실행해서는 이 네 마이그레이션이 적용되지 않는다.
3. **admin을 현재 형태로 공개하면 안 된다.** 인증 없는 service-role 조회/변경/삭제 API다. 이미 공개 배포됐는지는 미확인이다.
4. **billing 플래그를 현재 형태로 켜면 안 된다.** cancel 무인증, cron secret 없을 때 무인증, webhook secret 없을 때 서명 미검증, 첫 결제 금액 query string 신뢰 문제가 있다.

## 실운영 전 필요(P1)

1. 리드 수신 성공을 확인한 뒤에만 성공 응답하거나, 먼저 DB/outbox에 저장하고 웹훅 재시도·장애 알림을 두어야 한다.
2. 빠른 상담용 `leads` 테이블 또는 견적과 분리된 영속 저장 경로가 필요하다.
3. 운영 Supabase에 `001`~`006` 적용 여부를 migration history와 실제 컬럼으로 확인하고, `types.gen.ts`를 실제 생성 타입으로 교체해야 한다.
4. admin에 인증·권한검사·네트워크 접근 제한을 적용하고, 모든 API에서 서버 측 admin 권한을 확인해야 한다.
5. billing의 가격은 DB의 확정 금액을 서버에서 재계산해야 하며, cancel/구독 조회도 로그인한 고객 소유권을 필수 검증해야 한다.
6. `CRON_SECRET`, `TOSS_WEBHOOK_SECRET`은 “없으면 검증 생략”이 아니라 production에서 “없으면 시작/요청 거부”로 바꿔야 한다.
7. 실제 시공 사진으로 `public/curated` 스톡 자산을 교체하고, 대표전화·주소·대표자·사업자번호 등 실사업자 정보를 확정해야 한다.

## 나중(P2)

1. 사용하지 않는 Unsplash remote image 허용 설정 제거 (`apps/web/next.config.mjs:7-8`).
2. 입력 placeholder의 가짜 전화번호 형식을 실제 안내 문구 또는 중립 형식으로 정리.

4. 고객/관리자 알림 채널별 전송 결과를 관리자 화면에서 조회할 수 있도록 delivery log 추가.
